# Справочник полей: брони и гости (для интеграции с CRM)

## Назначение и статус документа

Документ описывает **состав полей** операций CRUD (создание, чтение, обновление, удаление) по **броням** и **гостям** в PMS: обязательность каждого поля и краткое пояснение. Он нужен для планирования интеграции с CRM-системой.

Важно понимать статус документа:

- Это **предварительный справочник возможных полей**, а не точная спецификация API.
- Эндпоинты, домены, форматы запросов/ответов, коды ошибок и авторизация здесь **не описаны намеренно** — они появятся в отдельной документации.
- При интеграции для CRM в будущем будет разработан **отдельный API и отдельная авторизация**; конкретные контракты (пути, схемы, токены) будут зафиксированы на этапе разработки этого API.
- Названия полей, их обязательность и справочные значения отражают **текущую внутреннюю модель PMS** и могут измениться к моменту разработки интеграции.

## 1. Ключевые понятия модели

Прежде чем читать таблицы полей, важно понимать структуру данных:

- **Бронь (Booking)** — это бронирование **одной комнаты** на период. Мультикомнатное бронирование создаётся как группа связанных броней (одна бронь на каждую комнату).
- **Заказчик/контакт (Customer) ≠ Гость (Guest)** — это две разные сущности:
  - **Заказчик** — тот, кто оформляет бронь: контактное лицо / плательщик. Указывается в броне (объект `customer`).
  - **Гость** — конкретное проживающее лицо, с паспортными данными для регистрации (в т.ч. для гос. регистрации иностранцев). Гости добавляются к броне поимённо.
- У брони есть **агрегатные счётчики** `number_of_adults` / `number_of_kids` — это просто числа (сколько человек проживает). Отдельно ведётся **список поимённых гостей**. Эти вещи не связаны напрямую: можно указать «2 взрослых», не заводя две карточки гостя.
- **Отмена ≠ удаление**:
  - **Отмена брони** — это смена статуса на «Отмена» (с указанием причины), а не удаление записи.
  - **Удаление** реализовано как «мягкое» (soft delete): запись помечается удалённой, но физически из базы не стирается.

## 2. Бронь — CRUD

### 2.1 Создание брони — поля

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `room_id` | int | **да** | Комната, которую бронируем (из справочника комнат отеля). Должна быть активной и принадлежать отелю. |
| `tariff_id` | int | **да** | Тариф бронирования. |
| `check_in_datetime` | datetime | **да** | Дата и время заезда. |
| `check_out_datetime` | datetime | **да** | Дата и время выезда. Должно быть позже заезда. |
| `number_of_adults` | int | **да** | Количество взрослых (1–100). |
| `number_of_kids` | int | нет | Количество детей (0–100). |
| `customer` | object | **да** | Заказчик/контакт брони (см. вложенные поля ниже). |
| `customer.name` | string | **да** | Имя заказчика. |
| `customer.surname` | string | нет | Фамилия заказчика. |
| `customer.patronymic` | string | нет | Отчество заказчика. |
| `customer.phone` | string | нет | Телефон заказчика. |
| `customer.email` | string | нет | Email заказчика. |
| `customer.iin` | string | нет | ИИН заказчика. |
| `customer.booking_method_id` | int | нет | Способ бронирования (справочник способов брони отеля). |
| `customer.marketings[]` | int[] | нет | Маркетинговые источники (откуда пришёл клиент). |
| `status_id` | int | нет | Статус брони (справочник §4). По умолчанию — «Забронирован». |
| `type_id` | int | нет | Источник/тип брони (справочник §4). |
| `company_id` | int | нет | Компания-заказчик (для корпоративных броней). |
| `booking_number_pms` | string | нет | Внутренний номер брони PMS. Обычно генерируется системой. |
| `booking_number_module` | string | нет | Номер брони во внешнем модуле бронирования. |
| `booking_number_ota` | string | нет | Номер брони в OTA (Booking.com и т.п.). Полезно для сопоставления с внешней системой. |
| `booking_datetime` | datetime | нет | Дата/время оформления. При создании обычно перезаписывается текущим временем. |
| `cancellation_datetime` | datetime | нет | Плановая дата отмены (для отложенных сценариев). |
| `discount` | decimal | условно | Размер скидки (число, до 2 знаков после точки). |
| `discount_type` | string | условно | Тип скидки: `relative` (проценты) или `absolute` (сумма). **Обязательно, если задан `discount`.** |
| `promo_code_ids[]` | int[] | нет | Применяемые промокоды (должны быть действующими). |
| `additional_services_types[]` | object[] | нет | Доп. услуги: `id` услуги и `day` (дата). |
| `comment` | string | условно | Комментарий (до 1024 символов). **Обязателен для тарифа «Универсальный».** |
| `no_extra_charge` | bool | нет | Без доплат. |
| `sum` | int | нет | Сумма брони. Для тарифов с автоматическим расчётом считается системой. |

> **Групповое (мультикомнатное) создание.** Отдельный сценарий: вместо одиночных `room_id`/`tariff_id`/`number_of_adults` передаётся массив `groups[]`, где в каждом элементе **обязательны** `room_id`, `number_of_adults`, `tariff_id`, а `number_of_kids`/`sum` — опциональны. Заказчик (`customer`), даты и скидки — общие для всей группы.

### 2.2 Обновление брони — поля

При обновлении **все поля опциональны** (частичное обновление — передаём только изменяемые). Набор полей тот же, что при создании (см. §2.1), плюс поля отмены:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| *(любое поле из §2.1)* | — | нет | Передаётся только то, что нужно изменить. |
| `cancellation_status` | int | условно | Причина отмены (справочник §4). **Обязательно, если `status_id` меняется на «Отмена».** |
| `cancellation_reason` | string | условно | Текстовое пояснение причины. **Обязательно, если `cancellation_status` = «Другая причина».** |

### 2.3 Отмена и удаление брони

- **Отмена** выполняется через **обновление** брони: `status_id` → «Отмена» (id `101`), плюс `cancellation_status` (обязательно) и при необходимости `cancellation_reason`. Запись при этом сохраняется.
- **Удаление** — «мягкое» (soft delete): бронь помечается удалённой, данные физически не стираются.

### 2.4 Чтение брони — возвращаемые данные

При чтении брони доступны (перечень основного):

- Идентификаторы и номера: внутренний id, `booking_number_pms`, `booking_number_module`, `booking_number_ota`.
- Статус, тип (источник), комната, тариф.
- Даты: заезд, выезд, оформление, отмена.
- Число гостей: `number_of_adults`, `number_of_kids`.
- Заказчик (контакт) и список поимённых гостей.
- Скидки, промокоды, доп. услуги, штрафы, комментарии.
- **Финансовый блок `sum`**: `accommodation` (проживание), `additional_service` (доп. услуги), `payment` (оплаты), `penalties` (штрафы), `paymentRefunds` (возвраты), `discount` (скидка), `overpayment` (переплата), `total` (итог). Доступ к финансовым данным ограничен правами пользователя.

## 3. Гость — CRUD

| `serial_number` | string | нет | Серия документа. |
| `main_guest` | bool | нет | Признак основного гостя брони. На одну бронь допускается только один основной гость. |
| `phone` | string | нет | Телефон (до 255). |
| `email` | string | нет | Email (до 255). |
| `comment` | string | нет | Комментарий. |
| `status_level_id` | int | нет | Уровень статуса постоянного гостя (справочник §4). |
| `purpose_visit_id` | int | нет | Цель визита (справочник целей визита). |
| `check_in_at` | datetime | нет | Фактическая дата/время заезда гостя. |
| `check_out_at` | datetime | нет | Фактическая дата/время выезда гостя (позже `check_in_at`). |

| `end_check_at` | datetime | нет | Окончание периода регистрации проживания (позже `start_check_at`). |

| `photos[]` | file[] | нет | Сканы/фото документов (jpg, jpeg, png, pdf; до 10 файлов). |

### 3.2 Обновление гостя — поля

При обновлении **все поля опциональны** (частичное обновление). Набор полей тот же, что при создании (§3.1), плюс:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| *(любое поле из §3.1)* | — | нет | Передаётся только то, что нужно изменить. |
| `booking_ids[]` | int[] | нет | Перепривязка гостя к броням (полная синхронизация связей гость↔брони). |

### 3.3 Удаление гостя

Удаление гостя — «мягкое» (soft delete). Данные сохраняются, запись помечается удалённой.

### 3.4 Чтение гостя — возвращаемые данные

При чтении гостя доступны все поля карточки (см. §3.1), а также связанные объекты:

- Тип гостя, гражданство, пол, тип документа, уровень статуса постоянного гостя — как вложенные объекты.
- Теги, связанные брони, фото документов.
- Вычисляемый блок проживания: `total_accommodation` (сумма за проживание), `total_additional` (сумма за доп. услуги), `total_nights` (число ночей), `last_checkout_booking` (последняя бронь с выездом).

## 5. Заметки для будущей интеграции с CRM

- **Отдельный API.** Текущий документ — только про модель данных, поэтому список полей может быть адаптирован под нужды CRM.
- **Заказчик ≠ гость.** Если CRM интересует «кто забронировал/контакт» — это заказчик (`customer`) брони. Если «кто фактически проживает» (для регистрации) — это поимённые гости.
- **ИИН.** Хранится как число (12 цифр). При передаче учитывайте возможную потерю ведущих нулей — рекомендуется трактовать как строку из 12 символов.
- **Идентификаторы справочников** зафиксированы, но значения лучше получать из справочных списков API — на случай их изменения/расширения.
